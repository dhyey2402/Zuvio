# Zuvio - Security Architecture

Security is treated as a first-class citizen at Zuvio. Frontend checks are considered purely cosmetic; all true authorization is enforced server-side.

## 1. Authentication & Session Management
* **Passwords:** Hashed exclusively with `bcrypt`. Plaintext passwords are never logged or stored.
* **Tokens:**
  * Stateless JWT for access tokens (short lifespan: e.g., 15 mins).
  * Opaque refresh tokens stored in an HttpOnly, Secure cookie to prevent XSS exfiltration.
* **CSRF:** Implemented since refresh tokens use cookies. A CSRF token must be passed in requests modifying state.

## 2. Authorization (RBAC)
* Access is validated against the resource ID.
* The system checks: 
  1. Is the user the owner? -> Full Access.
  2. Is the user in the `shares` table? -> Check `OWNER/EDITOR/VIEWER` permission level.
  3. Is this accessed via a valid `link_shares` token? -> Check link validity, expiration, and password.

## 3. Data Protection
* **Direct Storage Access:** Blocked. Object storage buckets are entirely private.
* **Signed URLs:** Time-bound URLs are generated by the backend for both uploads and downloads.
* **Public Links:** Use cryptographically secure random tokens (e.g., 32-byte hex strings generated by `secrets` module). Database UUIDs are NEVER used as share tokens to prevent ID scraping.
* **Public Link Passwords:** Hashed before storing in the database.

## 4. Input Validation & Abuse Prevention
* **Pydantic:** Strict schema validation rejects undefined or malformed payloads.
* **File Types:** Validated by checking the MIME type against an allowed list, and verified on the server post-upload.
* **File Limits:** Maximum size constraints enforced during the `init-upload` phase.
* **Rate Limiting:** Applied to authentication routes and link creation to prevent brute-forcing and spam.
